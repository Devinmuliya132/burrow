# 02 — Landscape: prior art, borrowings, and refusals

Before writing 400,000 lines of C, establish that it needs writing. This
document surveys what exists, concludes that the central thing does not,
identifies four projects whose *designs* we take wholesale, and records the
single most tempting shortcut — vendoring mature C libraries — as a decision
we deliberately refuse.

## 1. The thing itself does not exist

There is no project, partial or complete, that reimplements the Go standard
library in C. Searches turn up only the inverse (using C from Go, porting C to
Go) and one genuinely adjacent effort:

| Project | What it actually is | Overlap |
| --- | --- | --- |
| [KaisenAmin/c_std](https://github.com/KaisenAmin/c_std) | Reimplements the **C++** standard library in C — `std::array`, `std::forward_list`, containers, with Qt- and Python-inspired extras | Wrong library, right instinct. Demonstrates appetite. |
| [gccgo / libgo](https://gcc.gnu.org/) | GCC's Go frontend. Runtime support code in C/C++, but the library is *Go source compiled by gccgo* | Zero. Still needs Go source and a Go compiler. |
| [TinyGo](https://tinygo.org/) | LLVM-based Go compiler for embedded/WASM, with a reduced stdlib | Zero, and instructive: TinyGo's *reduction* of the stdlib is precisely the failure mode we are rejecting. |
| [libmill](https://github.com/sustrik/libmill) / [libdill](https://github.com/sustrik/libdill) | Go-style concurrency in C: `go(f(x))`, channels, `select` | Tier 0 only, and the most valuable prior art we have. §3 |
| [zelang-dev/c-coroutine](https://github.com/zelang-dev/c-coroutine) | C89 cooperative multitasking; libco+minicoro rework; `for_select` macro mirroring Go's `select`; **Windows supported, no `ucontext`** | Tier 0, and the only one that solves Windows. §3 |

The absence is not an accident of search terms; it is an accident of
incentives. Porting Go's library to C has no natural constituency — Go
programmers have it already, and C programmers have not historically expected a
library this good. The work is large, unglamorous, and mostly mechanical. That
is exactly the profile of work that is now newly tractable, and it is the
implicit thesis of this project.

**Consequence for the plan:** no incumbent to displace, no compatibility
pressure, no existing users — and therefore no organic adoption. Adoption has
to be bought with the deployment model. If `burrow` is not *trivially* easier to
adopt than writing the thing yourself, it fails regardless of quality. That is
why [15](15-build-deploy.md) is a first-class design document and not an
appendix.

## 2. What we take from SQLite

SQLite's amalgamation is the closest thing to a proven playbook for
"large C library that must be effortless to adopt," and the reasoning behind it
transfers almost without modification.

The facts: over 100 source files concatenated into one `sqlite3.c` of roughly
200,000 lines; archives under a quarter the size of the source tree; **5–10%
faster machine code** because single-translation-unit compilation gives the
compiler free cross-module inlining, dead-code elimination, interprocedural
register allocation and effectively free LTO; no `configure`, no Makefile, no
code-generation scripts to run because all generation already happened.
Crucially, the amalgamation is *canonical* — even a build from canonical
sources builds the amalgamation first — and it is generated by a script
(`tool/mksqlite3c.tcl`), never hand-maintained.

Four lessons, all adopted:

1. **Align the distribution format with the dominant use case.** People will
   copy two files into their tree. They will not adopt a build system.
2. **Generate, never curate.** The amalgamation is output. The tree stays
   modular; function prefixes and `static` scope preserve internal boundaries
   inside the single file.
3. **Convenience and performance can point the same way.** We get the same
   inlining win, and it matters more for us: `Str` and `Slice` operations
   are small functions called constantly, and cross-package inlining is the
   difference between competitive and embarrassing.
4. **Ship the split form too.** Some debuggers cannot handle source line
   numbers above 32,768, so SQLite also distributes `sqlite3-1.c`,
   `sqlite3-2.c`, … Given `burrow`'s size this is not optional; the split form
   is the default for the full build. → [15](15-build-deploy.md) §3

Where we go further: SQLite has *one* amalgamation because SQLite is one
product. `burrow` is 180 packages with a real dependency graph, and nobody wants
`go/types` in a firmware image. So the amalgamation is **parameterised**:
`burrow-gen --pkgs=net/http,encoding/json` walks the dependency closure and
emits exactly that. The generator is the product surface.

## 3. What we take from the C coroutine libraries

libmill established that Go's concurrency model transplants to C cleanly. Its
numbers are the ones to beat: roughly **20 million coroutine launches and 50
million context switches per second**, with a `go()` launch costing "a few
machine instructions" — cheap enough to be a routine flow-control construct
rather than a considered decision. That performance envelope is what makes
Go-style code natural in C; anything an order of magnitude worse and users
revert to callbacks.

libdill's contribution is different and more subtle: **structured
concurrency**. Lifetimes nest, children cannot outlive the scope that launched
them, and `hclose` on a bundle cancels every coroutine inside before returning,
with pending blocking calls beginning to return `ECANCELED`. Sústrik built this
specifically because Go has no way to cancel a goroutine — a real defect that
Go papers over with `context.Context` by convention.

This forces a genuine design choice, and we make it in Go's favour:

> **`burrow` goroutines are unstructured, like Go's, and `context` is the
> cancellation mechanism, like Go's.** Structured bundles are offered as an
> *additional* Tier 0 facility (`Bundle`) that `burrow`'s own
> internals use, but they are not imposed on `go(...)`.

Fidelity wins. A user porting Go code must not discover that goroutine
lifetimes are now scoped — that changes the meaning of every `go func()` in
their program. But we know libdill is right about leaks, so the escape hatch
exists and the arena allocator gives us a second, orthogonal answer: a
goroutine's arena dies with it, so leaked goroutines leak a bounded,
attributable amount of memory rather than an unbounded graph.
→ [06](06-runtime.md) §3

The limitations we must exceed are documented plainly by both libraries:
libmill and libdill are **POSIX-only** (no Windows), **single-core** — all
coroutines run on one CPU, multi-core requires multiple schedulers — and
**cooperatively scheduled** with no preemption, so a compute-bound coroutine
holds the CPU forever. None of those are acceptable for a Go-fidelity runtime.
Go is M:N across `GOMAXPROCS` cores with work stealing and asynchronous
preemption. `burrow` must match that, and that is the single largest piece of
genuinely novel engineering in the project. → [06](06-runtime.md)

`c-coroutine` matters for exactly one reason: it supports Windows and does not
use `ucontext`. Every POSIX-centric coroutine library reaches for
`swapcontext`, which does not exist on Windows and is slow where it does
(it makes a `sigprocmask` syscall per switch). The portable answer is
hand-written per-ABI context switch assembly — about 40 instructions per
architecture — which is what `minicoro`, `libaco` and Boost.Context all do.
→ [06](06-runtime.md) §2

## 4. The refusal: no vendored C libraries for ported packages

The shortcut is obvious. `compress/flate` → zlib. `regexp` → PCRE2.
`crypto/tls` → mbedTLS or OpenSSL. `unicode` → ICU or utf8proc. `math/big` →
GMP. Each would save thousands of lines.

Each is wrong, and the reason is the same every time: **the substitute has
different observable behaviour, which forfeits both fidelity and Go's tests.**

**`regexp` is the clearest case.** Go's engine is in the RE2 family: an
automata-based matcher that guarantees completion in linear time in the input
and in fixed stack space. PCRE2 is a backtracker. The differences are not
performance trivia:

- *Semantics.* RE2-family engines explore all alternatives simultaneously via
  an NFA simulation; backtrackers try alternatives in order and reset on
  failure. Nested choices can require exponentially many passes — the origin of
  ReDoS. `(a+)+b` on a pathological input is reported as making PCRE2 ~100×
  *slower* than RE2, while PCRE2-JIT is typically 2–5× faster on ordinary
  10 KB single-pattern work. Swapping engines changes the complexity class of
  every user's program, in a security-relevant direction.
- *Syntax and features.* RE2 deliberately omits constructs that require
  backtracking — backreferences and generalized assertions — "as a matter of
  principle". PCRE2 has them. A regex that compiles under PCRE2 and errors
  under Go is a fidelity bug in one direction; one that silently matches
  differently is worse.
- *No C option exists anyway.* RE2 is a C++ library. The C route is
  [CRE2](http://marcomaggi.github.io/docs/cre2.html/overview.html), a wrapper —
  which means a C++ toolchain, a C++ runtime, and a second ABI in the
  amalgamation. Non-starter for `cc burrow.c`.

Notably, Go's `regexp` and Rust's `regex` "don't share code with RE2, but
follow the same principles, accept the same syntax, and provide the same
efficiency guarantees." `burrow` becomes the third member of that set, ported
from Go's 6,601 lines, with Russ Cox's `swtch.com/~rsc/regexp` series as the
theory reference.

The same argument, compressed, for the others:

| Tempting | Why it fails fidelity |
| --- | --- |
| zlib / libdeflate for `compress/flate` | Go's tests pin *exact output bytes* per compression level. Go's encoder has its own Huffman-only, fast and level-1..9 matchers. Valid DEFLATE is not enough. |
| mbedTLS / OpenSSL for `crypto/tls` | Cipher-suite preference order, session-ticket format, ALPN behaviour, `tls.ConnectionState` contents, error strings, `VerifyConnection` hook points — all test-visible. And `crypto/tls`'s 15,225 test lines become useless. |
| ICU / utf8proc for `unicode` | Go pins a specific Unicode version per release with specific `RangeTable` contents. ICU is also 30 MB and a C++ dependency. We generate our tables from the same UCD input Go uses. |
| GMP for `math/big` | LGPL (a licence problem for embedders), and `math/big`'s API exposes `nat`-level behaviour, `Rat` exactness and `Float` rounding modes that do not map onto GMP's. |
| libcurl for `net/http` | Client only, wrong architecture, no server, and `net/http`'s value *is* its API shape. |
| PCRE2, ICU, GMP generally | Each adds a build dependency, which defeats `cc burrow.c`. |

**The inversion this buys us.** Porting rather than wrapping looks like more
work and is less, because Go's 440,736 lines of tests only apply to a port.
A wrapper has to have its tests rewritten to accommodate the substitute's
behaviour, at which point the tests no longer certify fidelity and the whole
verification strategy of [14](14-conformance.md) collapses. The tests are the
asset. Protect them.

**Where vendoring is fine.** Optional, additive, never on the fidelity path:
`mimalloc` as an allocator backend, Boehm GC as a memory backend
([05](05-memory.md) §5), `liburing` as a PAL acceleration on Linux, TSan for
`runtime/race`. All four are opt-in build flags, all four have a portable
fallback, and none of them can change a test result.

## 5. What we take from Zig

Zig's standard library passes `std.mem.Allocator` explicitly into every
function that allocates. This is the single most important borrowed idea in the
project and it resolves what would otherwise be an intractable problem.

The problem: Go's API allocates freely because a GC exists. A C *library*
cannot assume a GC — a bolt-on tracing collector forces its runtime onto every
consumer and, as the Boehm literature notes, conservative collectors identify
pointers by heuristic, so behaviour can shift with OS version or machine
memory. Meanwhile per-object `free` means specifying ownership 23,730 times,
distinguishing borrowed from owned returns at every boundary, and being right
every time. `strings.Split` returns sub-slices *aliasing* its input, so the
slice header is owned and the elements are borrowed — and that is one function
of 23,730.

Zig's convention collapses it: allocation is visible in the signature,
ownership is uniform, and the *policy* becomes the caller's choice rather than
the library's. `burrow` states it as one rule with no exceptions, which is the
only form in which a rule survives 180 packages. → [05](05-memory.md) §2

The corollary borrowed with it: **arena allocation makes the rule pleasant
rather than merely tractable.** Bump-pointer allocation is faster than
`malloc`, and dropping an arena frees everything at once, so the common case —
"do a lot of string work, then throw it away" — needs no per-object
bookkeeping at all and cannot leak.

## 6. What we take from Cosmopolitan

[Cosmopolitan Libc](https://justine.lol/cosmopolitan/) makes C
build-once-run-anywhere: `cosmocc` emits a polyglot Actually Portable
Executable that runs natively on Linux, macOS, Windows, FreeBSD, OpenBSD 7.3+,
NetBSD and BIOS, on x86-64 and aarch64, interpreted as a PE on Windows and as a
shebang-less shell script on Unix. The toolchain bundles GCC 14.1 and Clang 19,
and `MODE=tiny` produces ~20 KB binaries.

We do not depend on it, and we support it as a first-class toolchain. The
reasoning is that "easy to deploy" has two distinct meanings and Cosmopolitan
covers the second one:

1. *Easy to integrate* — two files, `cc burrow.c`. Solved by the amalgamation.
2. *Easy to distribute the result* — one binary for every OS. Solved, for
   people who want it, by `cosmocc`.

Practically this constrains the PAL: Cosmopolitan's libc surface is broad but
not infinite, and it does not want you calling raw syscalls. Since the PAL is
around forty entry points, `cosmo` becomes one more PAL backend rather than a
port. → [10](10-packages-os.md) §2, [15](15-build-deploy.md) §6

Known friction to document rather than discover: `zsh: exec format error`
needs zsh 5.9+, Linux users generally want the APE loader registered, and WSL
needs `binfmt_misc/WSLInterop` disabled. These go in the deployment doc's
troubleshooting section verbatim.

## 7. What we take from raylib and libgit2 (API ergonomics)

"Easy to use" is a requirement, and the two best-liked large C APIs are
instructive in opposite ways.

**raylib** is loved because it is *flat and guessable*: no handles to
initialise, no context object, no error codes to check for the common path,
consistent verb-noun naming, and defaults that work. Its cost is that it owns
global state and is not reentrant — unacceptable here.

**libgit2** is respected because it is *rigorous*: a uniform `git_` prefix,
every type has `_new`/`_free`, every fallible call returns `int` with a
thread-local last-error, and out-parameters come first. Its cost is verbosity —
five lines to do one thing.

`burrow` takes libgit2's rigour as the base layer and raylib's flatness as an
optional layer:

- Base: explicit allocator, explicit errors as return values (Go-style
  `(value, error)` becomes an out-parameter plus a returned `Error`), no
  global mutable state, fully reentrant.
- Convenience: a `BURROW_SHORT` opt-in that defines `strings_Contains` as an alias
  for `strings_contains`, plus a thread-local default allocator so
  `BURROW_SPLIT(s, sep)`-style macros can omit the allocator argument in scripts
  and tests. Off by default, never used inside `burrow` itself.
  → [08](08-naming-abi.md) §6

## 8. Summary of positions

| Question | Position |
| --- | --- |
| Does a Go-stdlib-in-C exist? | No. Confirmed absent, not merely unfound. |
| Distribution format | Generated per-selection amalgamation. SQLite's model, parameterised. |
| Concurrency prior art | libmill's performance target, libdill's cancellation insight, c-coroutine's Windows approach. Go's *semantics*. |
| Vendor mature C libraries? | **No**, for anything on the fidelity path. Yes, optionally, for allocators/GC/io_uring/TSan. |
| Memory model | Zig's explicit allocator passing. Non-negotiable. |
| Cross-platform binary story | Cosmopolitan as a supported PAL backend, not a dependency. |
| API ergonomics | libgit2 rigour by default, raylib flatness opt-in. |
