# 12 — Tier 4: crypto

Five top-level package trees, 794 exported declarations, 25,378 non-test lines,
44,013 test lines. Small by line count, and the highest-consequence code in the
project. This is also the tier where "port Go's implementation" is least
negotiable: a crypto library that is *nearly* right is worse than useless,
because it fails silently and the failure is exploitation.

`crypto/tls` is the gating dependency for `net/http` over HTTPS, which means
Tier 4 is sequenced before the HTTP work even though HTTP is the headline.
→ [11](11-packages-net.md) §5

## 1. The governing rule: no substitution

[02](02-landscape.md) §4 refused to vendor mature C libraries generally. In
crypto the refusal is strongest, and it needs stating because the obvious
objection is loudest here: *why not just link BoringSSL, or mbedTLS, or
libsodium?*

Because `crypto/tls`'s API is not "a TLS library". It is a specific object
graph — `tls.Config` with 40+ fields, `tls.Conn` implementing `net.Conn`,
`tls.ClientHelloInfo`, `GetCertificate`/`GetClientCertificate`/
`VerifyPeerCertificate`/`VerifyConnection` callbacks, `ConnectionState` with
its exact field set, session ticket key rotation, `CipherSuites` enumeration,
`CurvePreferences`, `NextProtos` ALPN, `tls.Dialer`, `QUICConn` for HTTP/3 —
and a set of behaviours that Go's 15,000 lines of TLS tests pin precisely.
Adapting mbedTLS to present that surface is more work than porting Go's TLS
stack, produces a result that diverges under every edge case, and throws away
the test suite that is the only reason to believe the result is correct.

The same argument applies to the primitives, with an additional one: Go's
`crypto/internal/fips140*` tree is a **FIPS 140-3 validated module boundary**
(§4), and that structure only means something if the code inside it is the
code that was validated.

**Escape hatch.** A `BURROW_CRYPTO_BACKEND=openssl` build mode is permitted for
the hash/cipher primitives only — `crypto/sha256`, `crypto/aes`, `crypto/hmac`
and friends dispatching to OpenSSL/BoringSSL where the ABI matches — for users
who need a certified vendor module or hardware offload. It is off by default,
it never covers `crypto/tls` or `crypto/x509`, and it is tested by the same
conformance suite. This mirrors Go's own `GOEXPERIMENT=boringcrypto`.

## 2. Primitives

| Area | Packages | Notes |
| --- | --- | --- |
| Hashes | `crypto/md5`, `sha1`, `sha256`, `sha512`, `sha3`, `hash/*` | assembly-accelerated in Go; C + intrinsics here (§6) |
| MAC/KDF | `crypto/hmac`, `hkdf`, `pbkdf2` | thin, mechanical |
| Block ciphers | `crypto/aes`, `des`, `rc4`, `cipher` | `cipher.AEAD`, GCM, CTR, CBC, CFB, OFB, and the interface contracts |
| Stream/AEAD | `crypto/chacha20poly1305` (via x/crypto vendor) | |
| Elliptic curves | `crypto/elliptic`, `ecdh`, `ecdsa`, `ed25519` | `nistec`/`edwards25519` field arithmetic, generated by `fiat-crypto` upstream |
| RSA | `crypto/rsa` | PKCS#1 v1.5, OAEP, PSS; blinding mandatory |
| Post-quantum | `crypto/mlkem`, `crypto/mldsa`, `crypto/hpke` | ML-KEM-768/1024, ML-DSA, HPKE — new in recent Go, required for X25519MLKEM768 hybrid key exchange in TLS |
| Randomness | `crypto/rand` | PAL-backed: `getrandom`, `arc4random_buf`, `BCryptGenRandom`; never a userspace CSPRNG |
| Misc | `crypto/subtle`, `crypto/cipher`, `crypto` (the registry) | `subtle` is load-bearing (§3) |

Two implementation notes that matter more than the rest:

**Field arithmetic.** Go's `nistec` and `edwards25519` packages contain
constant-time field element code that was *generated by* `fiat-crypto`, a
formally verified generator, and then hand-wrapped. `burrow` regenerates from
`fiat-crypto`'s C backend where possible — this is the one place in the project
where the C output is more natural than the Go — and ports the wrappers. Do not
hand-write modular arithmetic.

**`crypto/rand` is not portable code.** It is a PAL call.
[10](10-packages-os.md) §2 already enumerates it. It must never fall back to a
userspace generator, never buffer across `fork`, and never fail silently:
`rand.Read` errors are fatal in Go (it panics since Go 1.24) and must be here.

## 3. Constant-time discipline

The hard part of crypto in C is not writing the algorithms, it is keeping the
compiler from helping. The rules:

1. **All secret-dependent code uses `crypto/subtle`'s primitives** —
   `subtle_constant_time_compare`, `ConstantTimeSelect`,
   `ConstantTimeByteEq`, `ConstantTimeLessOrEq` — never `memcmp`, never `if`,
   never `?:` on secret data, never secret-dependent array indices, never
   secret-dependent division.
2. **`subtle`'s own implementations are compiled with optimisation barriers.**
   The standard trick — an empty `asm volatile("" : "+r"(x))` — is used on
   GCC/Clang. MSVC has no equivalent, so the MSVC build routes `subtle` through
   a separately-compiled translation unit with optimisation disabled via
   `#pragma optimize("", off)`. This is documented, ugly, and necessary.
3. **Secrets are zeroed** via a `crypto_wipe` that the compiler cannot elide
   (`SecureZeroMemory`/`explicit_bzero`/volatile-pointer memset fallback).
4. **Verification, not assertion.** Constant-timeness is checked, not claimed:
   - [`dudect`](https://github.com/oreparaz/dudect)-style statistical timing
     tests on every secret-dependent function, in CI, as a gate.
   - `valgrind --tool=memcheck` with secrets marked undefined (the
     ["ct-verif via memcheck"](https://www.imperialviolet.org/2010/04/01/ctgrind.html)
     technique): any branch or index on undefined data is reported.
   - Compiler-explorer-style assembly diffing on the `subtle` TU, pinned in
     tests, so an optimiser change that introduces a branch fails the build.
5. **No `-fprofile-use` or PGO on the crypto TU.** Profile-guided optimisation
   introduces data-dependent branches by design.

This is also why the amalgamation cannot be a single translation unit for
crypto: rule 2 requires separate compilation flags.
[15](15-build-deploy.md) §3 accounts for it — `burrow-crypto.c` is a second
file in the split, and the single-file form carries the pragma variant.

## 4. The FIPS 140-3 module boundary

Go 1.24+ restructured its crypto so that `crypto/internal/fips140` and
`crypto/internal/fips140/*` form a self-contained module that can be
FIPS-validated, with `GODEBUG=fips140=on|only` selecting it and a
`crypto/fips140` public package exposing `Enabled()`.

`burrow`'s position:

- **The structure is reproduced faithfully.** Same package boundary, same
  service indicator, same `fips140=on|only` behaviour, same startup self-tests
  (KATs, integrity check over the module's own bytes), same
  `fips140.Enabled()`.
- **No validation claim is made.** `burrow` is not FIPS validated, will not be
  unless someone funds a CMVP submission, and the documentation says so in
  those words. Claiming otherwise would be fraud.
- The structure is still worth having: it is where the algorithm restrictions
  and self-tests live, and `fips140=only` is a useful "reject non-approved
  algorithms" mode regardless of certification status.

The integrity self-test is the one part that genuinely differs. Go computes an
HMAC over the module's object code using linker-provided section bounds.
`burrow` does the same using `__start_burrow_fips`/`__stop_burrow_fips` section
markers on ELF, `__attribute__((section))` + `getsectiondata` on Mach-O, and
`#pragma section` on PE/COFF — the same mechanism as the reflect registry.
→ [07](07-reflect.md) §5

## 5. `crypto/tls` (103 decls, 8,000+ lines, 15,000+ test lines)

TLS 1.3 and 1.2, client and server, and nothing about it is optional.

- **Handshake state machines.** Four of them: TLS 1.2 client, 1.2 server, 1.3
  client, 1.3 server. Go's are written as straight-line code with explicit
  state structs rather than as a state machine, which ports well.
- **Extensions:** SNI, ALPN, session tickets (1.3 PSK resumption with
  `SessionState` encoding), key shares, signature algorithms, supported
  versions, OCSP stapling, SCTs, `RenegotiationInfo`, Encrypted Client Hello
  (ECH, in recent Go), post-quantum key share (X25519MLKEM768, which is now the
  default and non-negotiable for interop).
- **Record layer** with its exact limits, alert handling, and the
  `KeyUpdate` flow.
- **`tls.Config` fidelity.** Every field, including the awkward ones:
  `InsecureSkipVerify`, `Time`, `Rand`, `ClientAuth` modes,
  `SessionTicketsDisabled`, `SessionTicketKey` rotation, `Renegotiation`,
  `DynamicRecordSizingDisabled`, `EncryptedClientHelloKeys`. `Config.Clone`
  semantics included.
- **QUIC hooks** (`tls.QUICConn`, `QUICEvent`) for HTTP/3.
- **`GODEBUG` knobs**: `tlsmlkem`, `tls10server`, `tlsrsakex`,
  `tlsunsafeekm`, `x509sha1` and the rest, because they are part of how Go
  manages crypto deprecation and downstream users depend on them.

**Conformance.** TLS has the best external test infrastructure of any component
in the project and `burrow` uses all of it:

| Mechanism | What it gives |
| --- | --- |
| Go's `crypto/tls` tests | including the recorded-handshake `testdata` transcripts, which replay against OpenSSL/BoringSSL captures — free interop testing |
| BoringSSL's [`runner`](https://github.com/google/boringssl/tree/master/ssl/test) | the industry's most thorough TLS test suite; Go itself does not use it, so this is *better* coverage than Go's |
| `tlsfuzzer` | malformed-handshake resistance |
| Differential: `burrow` ↔ Go, OpenSSL, BoringSSL, rustls, NSS, both directions | interop matrix, nightly |
| Wycheproof test vectors | known-bad edge cases across all primitives |
| CAVP/ACVP vectors | KAT coverage for the FIPS module algorithms |

Wycheproof and ACVP vectors are the highest-value items in the whole
conformance plan: they are JSON files of algorithm inputs and expected outputs
that catch exactly the bugs a hand-port introduces. They run against the
primitives before `crypto/tls` is started.

## 6. Assembly and acceleration

Go's crypto is heavily assembly-optimised (AES-NI, SHA extensions, CLMUL for
GHASH, AVX2 ChaCha20, NEON equivalents). Portable C AES-GCM is roughly 20–40×
slower than AES-NI, which is not an acceptable HTTPS server.

The approach, in three layers:

1. **Portable C reference implementation for everything.** Always present,
   always correct, always constant-time, used on unknown architectures and as
   the differential oracle for the accelerated paths.
2. **Compiler intrinsics** (`<wmmintrin.h>`, `<arm_neon.h>`,
   `__builtin_ia32_*`) behind `#if defined(__AES__)`-style guards, with runtime
   CPU detection (`cpuid`, `getauxval`/`HWCAP`, `sysctlbyname` on macOS,
   `IsProcessorFeaturePresent` on Windows) selecting the implementation. MSVC
   supports the x86 intrinsics; this covers the primary platforms without
   leaving C.
3. **Optional hand-written assembly** for the few cases intrinsics cannot reach,
   behind `BURROW_ASM=1`, never required, never in the single-file
   amalgamation's default build.

Every accelerated path is tested against the portable path on random inputs, in
CI, on every architecture in the matrix. That test is trivial to write and it
is the thing that catches a mis-transcribed intrinsic.

## 7. `crypto/x509` (68 decls) and certificate handling

Certificate parsing and chain verification, which is where the non-obvious
security bugs live.

- **ASN.1/DER.** Go uses `encoding/asn1` for some things and
  `golang.org/x/crypto/cryptobyte` for the security-sensitive parsing, because
  `cryptobyte`'s explicit length-prefixed reader is much harder to get wrong.
  Port `cryptobyte` early; it is small, it is a joy in C, and everything
  security-sensitive should go through it.
- **Chain building** (`Certificate.Verify`) with its exact semantics: name
  constraints, key usage and EKU checking, path length, policy handling,
  `VerifyOptions`, and the specific ordering of returned chains.
- **System root pools** are platform code, and the most annoying part of
  `x509`: `/etc/ssl/certs` directory scanning with the distro-specific path
  list on Linux, the Security framework's trust settings on macOS (which
  requires evaluating per-certificate trust overrides, not just reading a
  bundle), and `CertOpenSystemStore` + `CertGetCertificateChain` on Windows.
  Go's platform verifier integration (`x509.Certificate.Verify` delegating to
  the OS on macOS and Windows) must be reproduced, because it is the only way
  to honour user-installed and enterprise trust policy.
- **`CertPool`**'s lazy-parse and dedup behaviour, `SystemCertPool`'s caching
  and `SSL_CERT_FILE`/`SSL_CERT_DIR` overrides.
- **Certificate generation** (`CreateCertificate`, `CreateCertificateRequest`,
  `CreateRevocationList`) — full write path, not just parse.

Conformance: [BetterTLS](https://bettertls.com/) for name constraints and path
building, `x509`'s own 10,000+ test lines, the CT log corpus for parse
robustness, and continuous fuzzing of the DER parser against Go's.

## 8. Tier 4 gate

1. All Wycheproof vectors pass for every implemented primitive.
2. All ACVP/CAVP vectors pass for the FIPS module algorithms; self-tests and
   integrity check work on all three primary platforms.
3. `dudect` and ctgrind report no timing leaks in `subtle`, `aes`, `rsa`,
   `ecdsa`, `mlkem`, or the GCM path — on every compiler in Tier A.
4. Accelerated paths agree with portable paths on 10^9 random inputs per
   primitive per architecture.
5. BoringSSL `runner` passes in both client and server mode.
6. TLS 1.3 and 1.2 interop with Go, OpenSSL 3.x, BoringSSL, rustls and NSS, in
   both directions, including session resumption, client certificates, ALPN and
   X25519MLKEM768.
7. BetterTLS passes.
8. `crypto/tls` + `crypto/x509` clean under ASan, UBSan, MSan and TSan.
9. **An external security review by a firm that does cryptography** has been
   completed and its findings addressed. Until then, `crypto` ships with a
   documented banner and `burrow` does not represent itself as production-ready
   for adversarial use. → [16](16-milestones.md) §6

Item 9 is not a formality and it is not skippable. It is the difference between
this project being useful and being dangerous. The primitives-and-vectors work
(items 1–4) is cheap and mechanical; the review is the expensive part, and it
should be scheduled and budgeted from the start rather than discovered at the
end.
